Momentum · Part 2 — the logic layer

Inside lib/: the seven files you need to understand before writing a backend

These files hold no visuals and no screens. They are the rules of your data — what a record looks like, how it's stamped, how it's saved, and how it's validated. Your server will end up re-implementing about half of what's in here, so read it as a specification for the API you're about to write.

First, a small correction to your mental model

You said "UI is in App.jsx and views, logic is in lib." Close, but the split is actually three layers, and the middle one matters most for your backend work:

The distinction is practical: lib/ files are "pure" helpers. Give one the same input twice and you get the same answer twice. They don't remember anything between calls and they don't know a screen exists. That's what makes them safe to reuse everywhere — and it's also why most of them will barely change when your backend lands.

How the seven files depend on each other

Notice storage.js stands alone: nothing in lib/ imports it, and it imports nothing from lib/. That isolation is deliberate — it's the piece you're going to replace.

lib/entities.js 27 lines · read this first

The rulebook for what a "record" is. Every task, goal, category and roadmap in the app is born here.

It exports four tiny things, and honestly this is the most important file in the project for you right now:

uid()      // makes a random-ish unique id string
nowISO()   // current time as "2026-08-04T09:31:00.000Z"
newEntity(fields)      // births a record
touch(entity, changes) // edits a record
alive(entity)          // is it not deleted?

The "envelope"

Every record, no matter what kind, is wrapped in the same four fields before its own data is added:

function newEntity(fields) {
  const t = nowISO();
  return { id: uid(), createdAt: t, updatedAt: t, deletedAt: null, ...fields };
}

So calling newEntity({ title: "Go to the gym", done: false }) gives you:

{
  id:        "m6x2k9q4a1b",
  createdAt: "2026-08-04T09:31:00.000Z",
  updatedAt: "2026-08-04T09:31:00.000Z",
  deletedAt: null,          // null means "alive"
  title:     "Go to the gym",
  done:      false
}

The ...fields part is JavaScript's spread syntax — "and then paste in whatever the caller passed." That's the whole trick: one function stamps every record type identically.

Editing: touch()

function touch(entity, changes) {
  return { ...entity, ...changes, updatedAt: nowISO() };
}

Read it right-to-left: copy the old record, paste the changes on top, then force updatedAt to now. It returns a new object rather than modifying the old one — React needs that to notice something changed. And because updatedAt is set last, no caller can accidentally forget to bump it.

Deleting: nothing is actually deleted

There's no delete function. "Deleting" is just an edit that fills in deletedAt, and alive() — literally e => !e.deletedAt — filters those out when drawing the screen. The record stays in storage forever.

What this means for your server

Three concrete decisions are already made for you. (1) Every table gets created_at, updated_at, deleted_at columns. (2) Your DELETE /tasks/:id endpoint runs an UPDATE … SET deleted_at = NOW(), never a real DELETE — and every GET must add WHERE deleted_at IS NULL. Forget that filter once and deleted tasks reappear. (3) Keep bumping updated_at on the server, not just trusting the client's value — it's how you'll later resolve "phone and laptop both edited this task" conflicts.

One thing to change when you go server-side: uid() generates ids in the browser using the clock plus a random suffix. Two browsers could theoretically collide, and a client can send you any id it likes. Let the database generate ids (a UUID column, or Mongo's _id) and return the created record in the POST response. The frontend can keep making temporary ids for optimistic display, then swap in the real one when the server answers.

lib/dates.js 32 lines · pure math

Turns dates into strings and back, and answers "which week is this in?"

Everything here is plain arithmetic on JavaScript's built-in Date. No library, no state. The important part isn't the functions — it's the two different date formats this app uses on purpose:

FormatLooks likeUsed forWhy
"YYYY-MM-DD"2026-08-04 task.date, goal.targetDate A calendar day with no time and no timezone. "Monday" should mean Monday no matter where you are.
ISO timestamp2026-08-04T09:31:00.000Z createdAt, updatedAt, deletedAt An exact moment, in UTC. Used for ordering and sync, never shown to the user.

The week logic is the one clever bit:

function weekStartOf(dateStr, weekStart) {
  const d = parseDate(dateStr);
  const diff = (d.getDay() - weekStart + 7) % 7;  // days since the week began
  d.setDate(d.getDate() - diff);                  // rewind to that day
  return fmtDate(d);
}

Given any date it walks backwards to the start of that date's week, where "start" is your Settings choice (0 = Sunday … 6 = Saturday, defaulting to Saturday). The + 7) % 7 is just a trick to keep the result positive when the subtraction goes negative. This single function is what makes the Weekly tab regroup instantly when you change your week-start day — it's recalculated on every render, never stored.

What this means for your server

Store task.date as a plain DATE column or a string — not a timestamp. If you use a datetime type, your database or driver will helpfully "convert timezones" and a task dated Aug 4 will come back as Aug 3 at 21:00 for some users. This is one of the most common bugs in first backends. Timestamps (createdAt etc.) are the opposite: always store those in UTC.

Also: don't build week-grouping endpoints. Send the raw tasks and let the frontend bucket them, exactly as it does now.

lib/config.js 41 lines · constants

The settings sheet: storage key names, the fixed dropdown values, and what a brand-new user starts with.

Four exports. STORE_KEYS is a lookup table of the five labelled boxes in localStorage:

export const STORE_KEYS = {
  goals:      "momentum_goals",
  tasks:      "momentum_tasks",
  roadmaps:   "momentum_roadmaps",
  profile:    "momentum_profile",
  categories: "momentum_categories",
};

They're written down once here so a typo in a key name — which would silently lose data — is impossible elsewhere in the app. These five names are your five API resources. That list is your backend's table plan, already decided.

Then EFFORT (low / mid / high with labels and colors) and GOAL_STATUS (active / paused / done) — fixed sets the user can't extend, so on the server they become enums or a CHECK constraint. And defaultCategories(), which returns the four starter categories (Work, Learning, Health, Personal) a new account begins with.

What this means for your server

Categories are deliberately data, not a hardcoded list — the user can add and rename them, so they need a real categories table. defaultCategories() becomes something your signup endpoint runs: create the user, then insert their four starter rows.

lib/storage.js 96 lines · ★ the main seam

The only file in the app allowed to read or write saved data. This is where your API will physically connect.

It does three jobs.

1. It picks a backend at startup

detectBackend() tries options in order and keeps the first that works: a special Claude storage object if the app is running inside Claude, otherwise localStorage, otherwise an in-memory Map that survives only until you close the tab. Each option is an object with the exact same two methods:

{
  id:    "local",
  label: "Saved in this browser",
  async get(key)        { ... },
  async set(key, value) { ... },
}

This is called the adapter pattern, and it's the single most valuable idea in the codebase. Because all three options answer to get and set, the rest of the app has no idea which one is in use. Adding a fourth — one that calls your API — means adding one more object to this file.

2. It converts objects to text and back

Browser storage can only hold strings, so saveJSON runs JSON.stringify on the way out and loadJSON runs JSON.parse on the way in. loadJSON also takes a fallback value and wraps everything in try/catch: if the saved text is corrupted, you get the fallback instead of a crashed app. Small detail, but it's why a bad write can't brick the app permanently.

3. It saves on a delay — useAutoSave

const timer = setTimeout(() => { /* save */ }, 350);
return () => { cancelled = true; clearTimeout(timer); };

This is debouncing. Every time your data changes, it schedules a save 350 ms in the future — and cancels any save that was already scheduled. So typing 20 characters into a field produces one write after you pause, not 20. The report() callback is what drives the "Saving… / Saved / Error" pill in the top-right.

Read this before you wire up the API. The obvious move is to make your API adapter's set() upload the whole array — "PUT all 400 tasks." It works, and it's a trap: you'd re-upload your entire task list every time you tick one checkbox, and two devices editing different tasks would overwrite each other wholesale.

The right move is to delete the five useAutoSave calls in App.jsx and instead fire one small request from inside each mutation function — toggleTask sends PATCH /tasks/:id, addTask sends POST /tasks, and so on. Each of those functions is already one line and already labelled with the endpoint it should become. Keep this local storage adapter afterwards as an offline cache.

lib/transfer.js 87 lines · the model for your validation

Export everything to a JSON file, and safely read one back in.

Export is simple: buildExport() wraps the five collections in a labelled envelope, and downloadJSON() does the browser trick for saving a file (build a Blob, make a temporary URL for it, create an invisible link, click it, throw it away).

{
  "app": "momentum",          // so we can reject other apps' files
  "version": 3,               // so future-you can read old files
  "exportedAt": "2026-08-04T…",
  "data": { profile, categories, goals, tasks, roadmaps }
}

parseImport() is the part worth studying. It assumes the file is hostile and checks, in order: is it valid JSON at all → is it an object → does app say "momentum" → is there a data key → is each collection an actual array. Every failure throws an error with a message written to be shown on screen ("That is not a Momentum backup file"), rather than a raw crash.

Note the deliberate asymmetry: strict about shape, forgiving about absence. A missing roadmaps key becomes an empty array; a roadmaps key holding the number 7 is an error. And notice who does what — SettingsView only parses the file, then hands the result up; App.jsx decides whether to apply it. Even here the "views never touch storage" rule holds.

What this means for your server

parseImport() is a working model of the mindset your entire API needs: never trust input. Every request body gets the same treatment — check the shape, reject clearly, and return a message safe to display. (In Node, libraries like zod do this for you.) Concretely, this envelope is also the easiest first endpoint to build: a POST /api/import that accepts this exact shape lets an existing local user move everything into their new account in one request.

lib/seed.js 61 lines · sample data

The example goals, tasks and roadmap you get if you choose "Load example data" during onboarding.

Not much logic, but one detail is worth copying. It builds the goals first, then grabs their generated ids to link the tasks:

const react = goals[1].id, gym = goals[2].id;
newEntity({ title: "Watch one React lesson", goalId: react })

That's a foreign key — a task doesn't contain its goal, it stores the goal's id and points at it. Same for goal.categoryId. This is exactly how the relationships will work in your database, and it's why parent records must be created before children.

lib/auth.js 17 lines · unused stub

Save, read and clear a login token in localStorage. Four small functions — and nothing in the app imports any of them.

I searched the whole src/ folder: saveToken, getToken and isLoggedIn are never called anywhere. It's a placeholder someone left for the backend that doesn't exist yet, and it isn't mentioned in the README's file map either. Nothing is broken — it's just dead code today.

It'll become real the moment you add login: the server returns a token, saveToken stores it, and every API request sends it back in an Authorization: Bearer <token> header so the server knows whose tasks to return.

Worth knowing now: storing tokens in localStorage is the simplest approach and fine while you're learning, but any script running on your page can read it. The sturdier option is an httpOnly cookie, which JavaScript can't touch at all. Don't let it block you — just know the tradeoff exists before this app has real users.

The five data shapes, in one place

This is the payoff of reading lib/ — you can now write your database schema. Every one of these also carries the four envelope fields (id, createdAt, updatedAt, deletedAt) except profile:

RecordIts own fieldsNotes for your schema
task title, date, done, effort, goalId date may be null ("someday"). effort is low/mid/high. goalId may be null — an unlinked task.
goal title, why, categoryId, targetDate, status status is active/paused/done. No progress column — progress is counted from linked tasks at render time.
category name, color User-owned and editable, so a real table — not an enum.
roadmap title, phases[] Nested two levels deep: phases hold items. See the note below.
profile name, theme, weekStart, onboarded A singleton, not a list — no id. Becomes columns on your users row.

Roadmaps are the one shape that forces a real decision. Right now a roadmap holds phases, and each phase holds items, all as nested objects with their own uid()s but no timestamps or soft delete. In a document database (MongoDB) you can store that nesting exactly as-is. In SQL you'd normally split it into three tables — or keep it as a single JSONB column, which is the closer match to how the app already behaves. Either is defensible; just decide deliberately rather than by accident.

Where to start, concretely

  1. Get the shapes into a database first. Five tables (or collections) matching the table above, each with the four envelope columns. No API yet — just prove you can store the shapes.
  2. Build read-only endpoints. GET /tasks, GET /goals, and so on, all filtering deleted_at IS NULL. Then add the fourth adapter in storage.js and check the app still renders with server data.
  3. Add writes one mutation at a time. Start with toggleTask → PATCH /tasks/:id, since it's the smallest. Each mutation in App.jsx is already one line and already labelled with the endpoint it becomes.
  4. Then, and only then, add login. That's when auth.js wakes up and every record gains a user_id. Doing this last means you debug one problem at a time.

The short version: entities.js defines your columns, config.js names your tables, dates.js tells you which columns are dates versus timestamps, transfer.js shows you how to validate input — and storage.js is the door you'll walk your API through.
