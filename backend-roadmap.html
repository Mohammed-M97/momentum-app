Momentum · Part 3 — the build plan

From a browser-only app to your own server, in nine steps

Built for your actual situation: one user — you — a hosted server you own, a password to get in, and the same data on your laptop and your phone. The ordering is the important part. Every phase below ends with a working app, so you're never staring at a broken project wondering which of six changes broke it.

The shape of the whole thing

The stack I'd pick for you

Your own roadmap inside the app already says Node.js basics → Express and REST APIs → MongoDB essentials → connect frontend to backend. That's a good plan and I'd stick to it — not because it's the only option, but because it means no new language. It's JavaScript on both sides, so everything you learn doing this transfers straight back to the code you already understand.

PiecePickWhy
ServerNode + ExpressSame language as your app. Express is the smallest thing that does the job.
DatabaseMongoDB (Atlas free tier)Your roadmap already names it, and it stores nested data natively — your roadmap → phases → items shape drops straight in with no redesign.
PasswordsbcryptTurns your password into a hash that can't be reversed. Never store the password itself.

The honest tradeoff on the database: Postgres is more common in job listings, and if the goal is your CV it's the more valuable thing to learn. Mongo is the faster path to a working app and the better fit for this particular data shape. Either is a fine answer — pick Mongo if you want momentum, Postgres if you want the resume line.

Stage one · on your own computer

Fix the data-loss bug

~30 minutes · do this before writing any server code

Right now loadJSON catches every error and returns an empty list, and App.jsx then sets hydrated = true without checking whether the load worked. The moment your data lives across a network, one dropped connection means: load fails → app thinks you have zero tasks → autosave saves that emptiness over everything.

The fix is to let load failures be visible instead of silent. Roughly:

// storage.js — separate "nothing saved yet" from "the read failed"
export async function loadJSON(key, fallback) {
  const raw = await store.get(key);        // let errors escape
  if (raw === null || raw === undefined) return fallback;
  try { return JSON.parse(raw) ?? fallback; }
  catch { return fallback; }               // corrupt text is still safe
}

// App.jsx — only mark hydrated if the load actually succeeded
try {
  const r = await Promise.all([ …the five loads… ]);
  …setState…
  setHydrated(true);
} catch (err) {
  setLoadError("Could not load your data. Reload to try again.");
  // hydrated stays false, so autosave never fires
}

Then show that error somewhere in the UI instead of rendering an empty app. Do this now, while everything is still local and easy to test.

Done when

You can break the load on purpose and the app says so, rather than showing you a cheerful empty task list.

Backend skeleton — running on your PC

a weekend · nothing about the app changes yet

A brand-new folder next to momentum-app. Don't touch the frontend at all in this phase.

  • npm init, install express, mongoose, cors, dotenv.
  • A free MongoDB Atlas cluster, with the connection string in a .env file.
  • One route: GET /health returning { ok: true }.
  • Confirm it connects to the database on startup.

Before anything else: create a .gitignore with .env and node_modules in it, on day one. Database passwords and login secrets pushed to GitHub get found by automated scanners within minutes. This is the single most common beginner accident, and it's completely avoidable.

Done when

Visiting localhost:3000/health in your browser returns ok, and the terminal says the database connected.

Schema, then move your real data in

a weekend

Define the five collections from the shapes you already know: tasks, goals, categories, roadmaps, profile. Every one gets createdAt, updatedAt, deletedAt.

Then the satisfying part — you already have a data importer. Open the app, go to Settings → Backup → Export, and you get a JSON file with everything in it. Write a small one-off script that reads that file and inserts it into Mongo. That's your real tasks and goals on a real server, before you've touched a single line of the frontend.

Two schema things not to get wrong. Store task.date and goal.targetDate as plain String in the "YYYY-MM-DD" format they already use — not as Mongo Date objects, or timezone conversion will shift your tasks a day. And there is no progress field on goals; it stays computed from tasks.

Done when

You can look inside Atlas and see your own real tasks sitting in the database.

Read from the server

a weekend · first time the app touches the backend

Add GET routes for the five collections, each filtering out soft-deleted records:

app.get("/api/tasks", async (req, res) => {
  const tasks = await Task.find({ deletedAt: null });
  res.json(tasks);
});

Then add the fourth adapter in lib/storage.js — the one the file's comments have been waiting for. Reading goes to the API; saving still goes to localStorage for now. Half-migrated on purpose: if the reads are wrong you'll see it immediately, and nothing can damage your server data yet.

Done when

You clear localStorage, reload, and your tasks still appear — because they came from the server.

Write to the server, one mutation at a time

a week or two · the biggest phase

Delete the five useAutoSave calls in App.jsx. They save whole collections at once, which across two devices means whichever device saves last silently erases the other's work. Replace them with one request per change, fired from inside each mutation.

Start with toggleTask — it's the smallest and easiest to verify:

const toggleTask = async (id) => {
  const task = tasks.find(t => t.id === id);
  setTasks(p => p.map(t => t.id === id ? touch(t, { done: !t.done }) : t));  // instant
  try {
    await api.patch(`/tasks/${id}`, { done: !task.done });                    // then confirm
  } catch {
    setTasks(p => p.map(t => t.id === id ? task : t));                        // put it back
    setSaveStatus({ state: "error", message: "Could not save" });
  }
};

That pattern — change the screen immediately, send the request, undo if it fails — is called an optimistic update. It's why good apps feel instant on a slow phone connection. Get it right once here, then repeat it for the other eight mutations: addTask, saveTask, softDeleteTask, saveGoal, setStatus, the two deletes, and the roadmap edits.

Done when

Every one of the nine mutations survives a page reload, and turning the server off produces a visible error instead of silent data loss.

Stage two · going public

Password and login

a weekend · this is the gate before deploying

Good news: you are the only user, so skip everything that makes auth hard. No signup page, no email verification, no password reset, no roles. What you actually need is four small pieces:

  1. One user in the database, created by a script you run once. Store bcrypt.hash(yourPassword, 10) — never the password itself. Even you shouldn't be able to read it back.
  2. POST /api/login — takes the password, compares with bcrypt.compare, and on success returns a signed JWT. On failure, a generic "wrong password" with a deliberate delay so it can't be hammered.
  3. Middleware on every other route that reads the Authorization: Bearer <token> header, verifies the signature, and rejects with 401 if it's missing or bad. Apply it to all five collections — one unprotected route is the same as no protection.
  4. A login screen in the app, plus lib/auth.js finally waking up: saveToken after login, getToken attached to every request, clearToken on logout, and a 401 response bouncing you back to the login screen.

On where the token lives. auth.js keeps it in localStorage, which means any script on your page could read it. The sturdier option is an httpOnly cookie — but with your frontend and backend on different domains, cookies need cross-site configuration that is genuinely fiddly to get right. For a single-user personal app, take the localStorage token, get it working, and know the tradeoff. Don't let this choice stall you for a week.

Non-negotiables regardless: a long random JWT_SECRET in .env and never in code, and a real password — this endpoint will be exposed to the entire internet in the next phase.

Done when

Requesting /api/tasks with no token returns 401, and the app sends you to a login screen instead of showing data.

Deploy all three pieces

a weekend, and expect it to fight you

Your project isn't a git repository yet, and almost every hosting platform deploys by pulling from GitHub — so git init, a first commit, and a private GitHub repo come first.

PieceWhereNotes
DatabaseMongoDB AtlasFree tier is plenty. You'll need to allow access from anywhere, since your server's IP isn't fixed.
BackendRailway or Fly.ioSet every .env value in the dashboard, not in the repo.
FrontendVercel or Netlifynpm run build, deploy dist/. Free and genuinely easy.

Two things will go wrong, and they go wrong for everybody:

  • CORS. Your frontend and backend are on different domains now, so the browser blocks the requests until the server explicitly allows that origin. Configure cors with your actual frontend URL — not *, now that there's a login token involved.
  • Cold starts. Free tiers on some hosts sleep after inactivity, so the first request takes 30+ seconds. For an app you open on your phone for ten seconds a day, that's genuinely miserable — pick a host that doesn't sleep, or budget a few dollars a month. Expect $0–5/month overall.
Done when

You open the URL on your phone, log in, and see the tasks you added on your laptop.

Stage three · making it pleasant

Make two devices actually agree

an evening · the fix you'll appreciate daily

After phase 6 it works, but the load effect in App.jsx runs once, on mount, and never again. Tick something on your phone, walk to your laptop, and the laptop shows yesterday's truth until you manually reload.

You don't need real-time sync for this. Refetch when the window becomes visible again:

useEffect(() => {
  const onVisible = () => { if (document.visibilityState === "visible") reload(); };
  document.addEventListener("visibilitychange", onVisible);
  return () => document.removeEventListener("visibilitychange", onVisible);
}, [reload]);

Switching to the tab or reopening the app on your phone now pulls fresh data. For one person who is only ever on one device at a time, this covers essentially every real case.

Done when

Add a task on your phone, switch to your laptop, and it's there without a manual refresh.

Make it feel like a phone app

an evening · optional but high reward

The app is already responsive and has a mobile bottom nav, so it's mostly there. What's missing is a public/ folder with a manifest.json and a few icon sizes — that's what turns "Add to Home Screen" into a real icon that opens without browser chrome.

If you want it to survive going offline, vite-plugin-pwa adds a service worker. Worth knowing: the app works offline today because everything is in localStorage, and moving to a server takes that away. Keeping the local adapter as an offline cache is the eventual answer — but it's a real project on its own, so leave it until the rest is running smoothly.

Done when

There's a Momentum icon on your phone's home screen that opens straight into the app.

If you only remember four things

  1. Phase 0 before anything else. It's thirty minutes now, or a lost task list later.
  2. Never deploy before phase 5. An unprotected API on the public internet is everyone's API.
  3. .env in .gitignore, first commit. Leaked secrets are the most common and most avoidable beginner accident.
  4. One phase at a time, and keep it working. Every phase above ends with something you can open and use. That's deliberate — when something breaks, you'll know it was in the last thing you touched.

Realistically this is six to eight weekends at a learning pace. The code you're starting from is unusually well set up for it — the seams are already in the right places, and each mutation is already labelled with the endpoint it's meant to become.
