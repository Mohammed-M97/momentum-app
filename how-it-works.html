How Momentum works, explained from zero

Momentum is a to-do & goals tracker that runs entirely in your browser. There is no server, no database, no account — your browser is the whole machine. This page walks through how the pieces fit together.

First, the 30-second version

Think of the app as a small office with three kinds of workers:

  • One manager (App.jsx) who keeps every piece of information — your tasks, goals, profile — in their head, and is the only one allowed to change anything.
  • Six screens (the views/ folder: Today, Tasks, Goals, Weekly, Roadmap, Settings) that just display what the manager gives them. When you click something, a screen doesn't act on its own — it reports the click back to the manager.
  • A notebook (lib/storage.js) where the manager writes everything down so nothing is lost when you close the tab. The notebook is your browser's built-in storage, called localStorage.

That's genuinely the whole design. Everything else is detail.

The big picture

Two words on that diagram that you'll see everywhere in React:

Props

The data a parent hands down to a screen. Like a manager handing a worker today's task list: "here, display this." The screen can read it but never change it.

Callbacks

Functions handed down alongside the data, so screens can report up. The Tasks screen doesn't tick a task itself — it calls toggleTask(id), which runs inside App.jsx.

The story of one click

The clearest way to understand the app is to follow a single click through it. Say you tick off the task "Go to the gym":

  1. You click the checkbox on the Tasks screen. The screen itself does nothing clever — it just calls the toggleTask function that App.jsx gave it as a prop.
  2. App.jsx updates its master list. It finds that task in its tasks list and flips done to true. This list in memory is called state.
  3. React redraws everything automatically. This is React's superpower: change the state, and every screen that uses it refreshes itself. The Tasks list shows the tick, the Today progress bar fills, the Weekly chart updates — with zero extra code.
  4. The autosave waits… then writes. A watcher in App.jsx notices the tasks changed. It waits 350 ms of quiet (so rapid clicks don't cause a save each), then asks storage.js to write the list to localStorage.
  5. The "Saved" pill appears. That little badge in the top-right is just the app reporting that the write succeeded.

Who lives in which folder

File / folderPlain-English job
index.htmlThe empty page the browser loads first. Nearly blank — React fills it in.
src/main.jsxThe ignition key. Its only job: start React and mount <App/> onto the page.
src/App.jsxThe manager. All data (state), all the functions that change it, which tab is open, autosaving.
src/views/One file per screen. They receive data and callbacks as props and just render. They never save anything themselves.
src/components/Reusable Lego bricks: icons, the Modal popup, the confirm dialog, progress bars.
src/lib/The toolbox — pure logic, no visuals. Date math, the storage notebook, export/import, ID stamping.
src/styles/momentum.cssEvery color, font, and spacing rule. The light/dark themes both live here.
package.jsonThe shopping list: which libraries the app needs (React) and the commands (npm run dev).
node_modules/The delivered shopping — thousands of files npm downloaded. Never edit; can always be re-downloaded.
vite.config.js · dist/Vite is the dev server and bundler: it runs the app while you develop and packs it into dist/ for publishing.

Five ideas the code is built on

State = the single source of truth

All data lives in one place (App.jsx). Screens never keep their own copies, so nothing can ever be out of sync.

Nothing is ever really deleted

Deleting a task just stamps it with deletedAt — a "soft delete." The alive() helper hides stamped items. Mistakes stay recoverable.

Goal progress is computed, not stored

A goal's % bar is counted from its linked tasks on every redraw. Since it's never written down, it can never be wrong or stale.

The Weekly tab stores nothing

Every chart there is a live calculation over your tasks. Change your week-start day in Settings and history regroups instantly — no data changed.

Storage is swappable

storage.js picks the best available notebook (localStorage, or memory as a fallback). One day a real server can be added there — and no screen will need to change.

The one rule that holds it all together

Screens never touch storage. Every screen gets its data and its callbacks from App.jsx, and all saving goes through storage.js. Because of this one separation, replacing localStorage with a real online backend later means editing one seam — not rewriting six screens. The comments marked BACKEND HOOK in the code point at exactly those spots.

Where your data actually is (and its one weakness)

Everything you type is stored in your browser's localStorage under keys like momentum_tasks — small labelled boxes that survive closing the tab and restarting the computer.

But: it belongs to this browser on this computer. Clear your browsing data, or open the app on your phone, and it's gone or empty. That's why Settings → Backup exists — Export writes all your data into one JSON file you can keep, and Import loads it back. Use it.

What happens when you run npm run dev

  1. Vite starts a tiny local web server at localhost:5173 — "localhost" just means this computer.
  2. Your browser asks it for the page. Vite serves index.html, translates the .jsx files into plain JavaScript on the fly, and sends everything over.
  3. React boots and App.jsx loads your data from localStorage — if it finds none, you get the onboarding screen instead.
  4. While you edit code, Vite hot-swaps the changes into the running page, usually without even losing your place. That's why saves show up instantly.

That's the whole machine: one manager holding the state, six screens rendering it, one notebook persisting it — and a single rule keeping them honest.
