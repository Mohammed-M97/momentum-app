Momentum · Part 4 — server side

The Momentum API: every piece you need to build, and the order to build it

Part 3 was the whole journey. This is the server itself — the folders, the five models, every endpoint mapped to the exact function in your app that calls it, and the beginner traps that cost people a full evening each. One user, one password, hosted somewhere real.

What a backend actually is

Strip away the jargon and a server is one loop: a request arrives, it passes through a line of checkpoints, something reads or writes the database, and a response goes back. Express calls those checkpoints middleware, and they run in the order you register them — which is the single most useful thing to understand about Express.

Something in your code that changes the plan

Reading how App.jsx hands data to the screens, there's a split you should know about before you start, because it affects two of your five collections.

Tasks and goals follow the pattern the README promises. Each change is its own small named function, already labelled with the endpoint it becomes — toggleTask, addTask, setStatus, and so on. Nine of them. Converting those to API calls really is mechanical.

Categories, roadmaps and profile don't. Look at what gets passed down:

<RoadmapView   roadmaps={roadmaps} onChange={setRoadmaps} … />
<CategoryModal categories={categories} onChange={setCategories} … />
<SettingsView  profile={profile} setProfile={setProfile} … />

Those are the raw React state setters handed straight to the view. So when you add a phase to a roadmap, RoadmapView builds an entirely new roadmaps array itself and passes it back. There's no addPhase function in App.jsx to hang an API call on — the app never learns what changed, only that something did.

What this means practically: you'll need a small refactor before those three can talk to an API — pull named mutations up into App.jsx (addPhase, toggleItem, renameCategory, updateProfile…) so each one has a place to put its request. It's not hard, it's just work nobody warned you about.

Do it collection by collection, right before you wire that collection up — not all at once up front. And do tasks and goals first, since they're already ready and they're 90% of what you actually use.

The five models

You already know these shapes from lib/entities.js. Every collection except the user carries the same four envelope fields:

// the envelope, on every model
id:        { type: String, required: true, unique: true, index: true },
createdAt: { type: String },   // ISO timestamp
updatedAt: { type: String },
deletedAt: { type: String, default: null },   // null = alive
userId:    { type: String, index: true },
ModelIts own fieldsWatch out for
User passwordHash, name, theme, weekStart, onboarded Profile is a singleton, so it is the user row — don't make two collections. Never a password field, only the hash.
Task title, date, done, effort, goalId date is a String, not a Date. goalId and date can both be null.
Goal title, why, categoryId, targetDate, status No progress field, ever. status is active|paused|done.
Category name, color Created for you at signup — the four defaults from config.js.
Roadmap title, phases[] Phases and items nest inside as plain objects with their own ids and no timestamps. Store the nesting as-is.

The id trap, and it will get you. Your app generates its own string ids via uid() and every record refers to others by them — task.goalId, goal.categoryId. Mongo, meanwhile, adds its own _id ObjectId to everything. If you let the frontend start seeing _id, every one of those links breaks.

Keep id as a real indexed field, and strip Mongo's extras on the way out so the frontend never knows the difference:

schema.set("toJSON", {
  transform: (doc, ret) => { delete ret._id; delete ret.__v; return ret; }
});

Do that once per model and your existing screens keep working untouched.

Every endpoint, and who calls it

This is the whole API. The right-hand column is the function in App.jsx that will make the call, so you can work through it line by line.

Goals — ready to go, with one interesting case

MethodRouteCalled by
GET/api/goalsinitial load
POST/api/goalssaveGoal, create branch
PATCH/api/goals/:idsaveGoal edit branch, and setStatus
DELETE/api/goals/:id?cascade=trueaskDeleteGoal — see below

Deleting a goal is the one endpoint that isn't a one-liner. The app asks whether to delete the linked tasks too, so the server has to do two things in one request: soft-delete the goal, then either soft-delete its tasks (cascade=true) or unlink them by setting goalId to null. Get both branches right — the unlink case is the one people forget, and it strands tasks pointing at a goal that's gone.

Categories, roadmaps, profile — refactor first

Roadmaps are the exception to "one small request per change." Phases and items are nested objects without timestamps or soft delete, so there's nothing sensible to PATCH individually. Sending the whole roadmap document on every edit is the right call here — they're small, and you only have one or two. Accept the inconsistency; the alternative is inventing sub-resources for data that isn't shaped that way.

Deleting a category is a genuine design decision the app doesn't currently make for you: goals store categoryId, so removing a category leaves them pointing at nothing. Either block the delete while goals still use it, or null out those categoryIds. Pick one deliberately rather than discovering it later.

Auth and bulk

MethodRouteNotes
POST/api/loginpassword in, token out. The only unprotected route.
GET/api/meis my saved token still valid? Called on app start.
GET/api/bootstrapall five collections in one response
POST/api/importaccepts the transfer.js envelope as-is
POST/api/resetaskReset — erase everything

Build /api/bootstrap and use it. Your app loads five collections at startup. Five separate requests over phone data is five round trips before anything renders; one request returning all five is noticeably faster on mobile — which is exactly where you'll be using this. The individual GETs are still worth having for refreshes.

The password, concretely

You're the only user, so skip signup, email verification, password reset, and roles. Four pieces:

// scripts/createUser.js — you run this ONCE, from your terminal
const hash = await bcrypt.hash(process.env.INITIAL_PASSWORD, 10);
await User.create({ id: uid(), passwordHash: hash, name: "…", weekStart: 6 });

// routes/auth.js
router.post("/login", async (req, res) => {
  const user = await User.findOne();
  const ok = user && await bcrypt.compare(req.body.password, user.passwordHash);
  if (!ok) return res.status(401).json({ error: "Wrong password" });
  const token = jwt.sign({ uid: user.id }, process.env.JWT_SECRET, { expiresIn: "30d" });
  res.json({ token });
});

// middleware/requireAuth.js — guards every other route
const header = req.headers.authorization || "";
const token = header.startsWith("Bearer ") ? header.slice(7) : null;
if (!token) return res.status(401).json({ error: "Not signed in" });
try { req.user = jwt.verify(token, process.env.JWT_SECRET); next(); }
catch { res.status(401).json({ error: "Session expired" }); }

Then in server.js, mount it once so you can't forget a route:

app.use("/api/login", authRoutes);      // open
app.use("/api", requireAuth);            // everything after this line is protected
app.use("/api/tasks", taskRoutes);
app.use("/api/goals", goalRoutes);       // …and so on

Rate-limit the login route. It's the one door open to the entire internet, and without a limit someone can try passwords as fast as your server answers. express-rate-limit capping it at a handful of attempts per fifteen minutes is about six lines and closes the whole problem. Use a long random JWT_SECRET — openssl rand -hex 32 — and keep it in .env.

Four traps that each cost an evening

  1. Forgetting app.use(express.json()). Without it req.body is undefined on every POST and the error tells you nothing useful. Register it before your routes.
  2. Async errors vanishing. In Express 4, an await that rejects inside a handler isn't caught — the request just hangs forever with no error printed. Wrap handlers in try/catch, or install express-async-errors once at the top of server.js. Express 5 fixes this natively.
  3. Forgetting deletedAt: null in a query. Miss it in one place and deleted tasks quietly reappear in that one screen. Consider a tiny shared helper so the filter is never hand-typed.
  4. Atlas IP allowlist. Your hosted server's IP isn't fixed, so a default allowlist blocks it and you get a connection timeout that looks like a code bug. Allow access from anywhere and rely on the database password.

Build order for the server

Same principle as before: every step ends with something you can actually check.

Skeleton

an evening

npm init, install express cors dotenv, one GET /health route, .gitignore with .env in it before the first commit.

Database connection

an evening

Free Atlas cluster, connection string in .env, mongoose.connect in db.js. Print a clear message on success and on failure.

Models, then your real data

a weekend

Write the five schemas with the toJSON transform. Then run createUser.js to set your password, and importBackup.js to load the JSON you exported from Settings → Backup. Look inside Atlas and see your own goals sitting there.

All the GET routes

an evening

Five collections plus /api/bootstrap, every one filtering deletedAt: null. Test them in your browser or Postman — no frontend involved yet.

Task writes

a weekend

POST, PATCH and the soft DELETE for tasks only. Get validation and the error shape right here, on one small resource, because you're about to repeat this pattern four more times.

Goals, then the other three

a weekend

Goals including the cascade/unlink branch. Then categories, roadmaps and profile — refactoring each one's frontend mutations out of the view as you reach it.

Lock the door

a weekend · before anything is public

bcrypt, JWT, requireAuth mounted so it covers everything but login, rate limiting on login. Verify by requesting /api/tasks with no token and getting a 401.

Harden, then ship

an evening

A single error-handling middleware returning a consistent { error } shape, helmet for security headers, and cors restricted to your real frontend URL rather than *.

Roughly five or six weekends of server work, and it slots into phases 1–5 of the main roadmap. Start with tasks and finish tasks completely — once one resource works end to end, the other four are the same shape with different fields.
