Momentum · reading the front end by tracing, not by reading

Four actions, traced end to end.

You don't read a React app top to bottom. You pick one thing a person can do, and follow the signal: which button, which function, which state, which file on disk, who reads it back. Do that four times and the shape of the whole app falls out.

Button→ Function→ State→ Storage→ Read back on load

The key · learn this once

Five lanes. Every trace runs through the same five.

Colors are consistent for the rest of the page. Once you know the lanes, you can read any trace below at a glance.

Screen

src/views/*.jsx · src/components/ui.jsx

Draws pixels and catches clicks. Holds only throwaway state — what you're typing, which tab is open. Never decides anything permanent.

Backend impact: almost none. These files barely change.

Brain

src/App.jsx

Owns all five collections. Every real change to your data happens in one of its mutation helpers — nowhere else.

Backend impact: this is where every API call goes.

Rules

src/lib/entities.js · dates.js · config.js

Pure functions. Give them input, get output. No state, no network, no surprises.

Backend impact: id creation moves to the server; the rest stays.

Persist

src/lib/storage.js

The only file in the project that touches localStorage. Turns objects into text and back.

Backend impact: this is the seam — it becomes HTTP.

Bytes

browser localStorage · five keys

momentum_profile · momentum_categories · momentum_goals · momentum_tasks · momentum_roadmaps

Backend impact: replaced by five MongoDB collections.

Trace 01 · create

The user adds a task

Type a title, press Add. Nine hops from your finger to the bytes on disk.

1
ScreenThe buttonviews/TasksView.jsx:72
<button className="btn primary" onClick={submit} disabled={!draft.trim()}>Add</button>

Pressing Enter in the text box calls the same submit — line 64. Two doors, one function.

2
ScreenWhat you typed lives here, and only hereviews/TasksView.jsx:17-19
const [draft, setDraft]   = useState("");
const [effort, setEffort] = useState("low");
const [goalId, setGoalId] = useState("");

This is form state, not app data. It is never saved anywhere. Refresh the page mid-typing and it's gone — correctly so.

3
Screensubmit() — validate, hand off, clearviews/TasksView.jsx:28
const submit = () => {
  const title = draft.trim();
  if (!title) return;                                // no empty tasks
  onAdd({ title, date: activeDate, effort, goalId: goalId || null });
  setDraft("");                                     // clear the box
};

Notice what it does not do: it doesn't create an id, doesn't add to a list, doesn't save. It packages a request and calls a prop it was handed. This is "callbacks up".

4
BrainWhere onAdd actually came fromApp.jsx:329
<TasksView tasks={tasks} goals={goals} categories={categories}
  onAdd={addTask} onToggle={toggleTask}
  onEdit={(t) => setTaskModal(t)} onDelete={askDeleteTask} />

Data flows down as props (tasks), intentions flow up as functions (onAdd). The view never knew what onAdd was — that's the point.

5
BrainaddTask — the one real mutationApp.jsx:157
/* BACKEND HOOK: POST /tasks */
const addTask = (t) => setTasks((p) => p.concat([newEntity({ done: false, ...t })]));

p.concat([...]) builds a brand-new array instead of pushing into the old one. React only re-renders when it sees a different array — push would change nothing on screen.

6
RulesnewEntity stamps the envelopelib/entities.js
export function newEntity(fields) {
  const t = nowISO();
  return { id: uid(), createdAt: t, updatedAt: t, deletedAt: null, ...fields };
}

Your bare { title, date, effort, goalId } becomes a full record. Every goal, task, category and roadmap wears this same four-field envelope — that's why one backend pattern covers all of them.

7
BrainReact re-renders, the row appearsApp.jsx:73 → 328
const [tasks, setTasks] = useState([]);   // changed → App re-runs
// → TasksView gets the new array → filters it → new <li> on screen

Nothing has been saved yet. The task is on screen and in memory only. If the browser crashed right now, it would be lost.

8
Persist350ms of silence, then autosave firesApp.jsx:131 → lib/storage.js:84
useAutoSave(STORE_KEYS.tasks, tasks, hydrated, report);   // App.jsx:131

// storage.js — waits, then writes the WHOLE array
const timer = setTimeout(() => {
  report({ state: "saving" });
  saveJSON(key, value).then(() => report({ state: "saved" }));
}, 350);

That "Saving / Saved" pill in the top bar is this line talking. The debounce exists so typing doesn't fire a write per keystroke.

9
BytesOne key, one big stringlib/storage.js:59
async set(k, v) { localStorage.setItem(k, v); }
// key:   "momentum_tasks"
// value: JSON.stringify(entire tasks array)

All your tasks are one string under one key. Adding a single task rewrites every task you own.

Take

The view collected input and asked. App.jsx decided and changed the data. lib/ did the pure work. storage.js wrote it down. That split holds for every action in the app.

For your backend: step 5 is the only line that needs to change. addTask becomes a POST /api/tasks, and step 6's uid() moves to the server so two devices can't invent the same id.

Trace 02 · update

The user edits a task

Two flavours, and the difference matters. Ticking a checkbox sends an id. Opening the editor sends a whole object.

1
ScreenFast path — the checkbox sends only an idviews/TasksView.jsx:90
<button className={"check" + (t.done ? " on" : "")} onClick={() => onToggle(t.id)}>

The view doesn't compute the new value. It says "this one changed" and lets the brain work out what that means.

2
BraintoggleTask — copy the list, replace one itemApp.jsx:159
/* BACKEND HOOK: PATCH /tasks/:id  { done } */
const toggleTask = (id) =>
  setTasks((p) => p.map((t) => (t.id === id ? touch(t, { done: !t.done }) : t)));

map returns a new array where every task is the same object except one. This exact three-part shape — map, match the id, touch — is the update pattern everywhere in this codebase.

3
Rulestouch — change fields, bump the clocklib/entities.js
export function touch(entity, changes) {
  return { ...entity, ...changes, updatedAt: nowISO() };
}

Every edit in the app goes through touch, so updatedAt is always honest. When two devices sync, that field is how you decide which version wins.

4
ScreenSlow path — the pencil opens a dialog and changes nothingviews/TasksView.jsx:100 → App.jsx:329
onClick={() => onEdit(t)}                // TasksView
onEdit={(t) => setTaskModal(t)}         // App wires it to a piece of UI state

{taskModal && <TaskModal task={taskModal} goals={goals} onSave={saveTask} />}   // App.jsx:351

taskModal holds which task is being edited. Set it and the dialog exists; set it back to null and the dialog is gone. That's the whole modal system.

5
ScreenThe dialog edits a private copyviews/TasksView.jsx:117
const [d, setD] = useState({
  title: task.title, effort: task.effort, goalId: task.goalId || "",
  schedule: task.date === null ? "backlog" : "date", date: task.date || todayStr(),
});

A draft. Typing here doesn't touch the real task, which is exactly why Cancel works — nothing was ever changed to undo.

6
BrainSave changes — the finished object goes upviews/TasksView.jsx:122 → App.jsx:161
// the dialog builds the whole new task itself
onSave(touch(task, { title, effort: d.effort, goalId: d.goalId || null,
                 date: d.schedule === "backlog" ? null : d.date }));

/* BACKEND HOOK: PATCH /tasks/:id  (full edit) */
const saveTask = (task) => {
  setTasks((p) => p.map((t) => (t.id === task.id ? task : t)));
  setTaskModal(null);                       // close the dialog
};

One function, two jobs: swap the record, dismiss the dialog. Then the same 350ms autosave from Trace 01 writes the whole array again.

Take

Modals are just state. taskModal is null or a task — nothing more. The same trick runs goalModal, catModal and confirm.

For your backend: both paths land on PATCH /api/tasks/:id. The checkbox sends { done }, the dialog sends the edited fields. Let the server set updatedAt — a phone with a wrong clock shouldn't get to stamp your data.

Trace 03 · delete

The user deletes a task

The most surprising trace in the app: the delete button never deletes anything, and the row that vanished is still in the array.

1
ScreenThe trash iconviews/TasksView.jsx:101
<button className="icon-btn danger-hover" onClick={() => onDelete(t)}>

Sends the whole task, not just the id — because the confirmation message needs the title.

2
BrainaskDeleteTask deletes nothing — it asksApp.jsx:165
const askDeleteTask = (task) => setConfirm({
  kind: "task", title: "Delete this task?",
  message: '"' + task.title + '" will be removed.',
  onConfirm: () => { softDeleteTask(task.id); setConfirm(null); },
});

The clever bit: onConfirm is a function stored inside state, and it already remembers which task you clicked. The dialog stays completely generic.

3
ScreenOne dialog serves every deletion in the appApp.jsx:353 → components/ui.jsx:45
{confirm && (
  <ConfirmDialog title={confirm.title} message={confirm.message}
    onCancel={() => setConfirm(null)}
    onConfirm={() => confirm.onConfirm(deleteLinked)} />
)}

Tasks, goals, roadmaps, phases, reset, import — all six confirmations are this one component. Cancel is simply setConfirm(null): forget the question was asked.

4
BrainsoftDeleteTask — a timestamp, not a removalApp.jsx:163
/* BACKEND HOOK: DELETE /tasks/:id  (server sets deletedAt) */
const softDeleteTask = (id) =>
  setTasks((p) => p.map((t) => (t.id === id ? touch(t, { deletedAt: nowISO() }) : t)));

Same map + touch as an edit. The array is still the same length. Nothing was thrown away.

5
RulesSo why did it disappear? A filter, one line up the fileviews/TasksView.jsx:25 · lib/entities.js
export const alive = (e) => !e.deletedAt;                    // entities.js

const list = tasks.filter((t) => alive(t) && ...);            // TasksView.jsx:25

The row vanished because the screen stopped drawing it, not because the data left. Every list in the app filters through alive.

6
BytesThe dead row gets saved toolib/storage.js:76
// the array written to disk still contains it:
{ "id": "mdq7k0zj4hp", "title": "Old task I deleted",
  "deletedAt": "2026-08-09T10:05:40.213Z" }

Open your exported backup and you'll see them. That's not a bug — it's what makes undo, history and multi-device sync possible later.

Take

Deleting a goal is the same trace with one extra branch: askDeleteGoal (App.jsx:184) counts the linked tasks and offers a checkbox — either mark those tasks deleted too, or just set their goalId to null and let them survive.

For your backend: DELETE /api/tasks/:id must set deletedAt, never actually remove the document. If the server hard-deletes, the other device has no way to learn the row is gone.

Trace 04 · boot

The page loads for the first time

Everything above wrote data. This is the only trace that reads it back — and it's the one your backend changes most.

1
ScreenOne script tag, one divindex.html:9-10 → src/main.jsx:6
<div id="root"></div>
<script type="module" src="/src/main.jsx"></script>

createRoot(document.getElementById("root")).render(<App />);

The entire app is drawn by JavaScript into one empty div. There is no other HTML file.

2
BrainEvery collection starts emptyApp.jsx:68-74
const [hydrated, setHydrated]     = useState(false);
const [profile, setProfile]       = useState(DEFAULT_PROFILE);
const [categories, setCategories] = useState([]);
const [goals, setGoals]           = useState([]);
const [tasks, setTasks]           = useState([]);
const [roadmaps, setRoadmaps]     = useState([]);

React renders before it reads anything. hydrated is the flag that means "the real data has landed" — remember it, it's about to matter twice.

3
BrainFirst paint is the spinnerApp.jsx:270
if (!hydrated) return <div className="loading">…Loading your data…</div>;

This guard is why you never see an empty task list flash before your real tasks appear.

4
BrainThe load effect — runs exactly onceApp.jsx:88-107
useEffect(() => {
  (async () => {
    const r = await Promise.all([
      loadJSON(STORE_KEYS.profile, null),  loadJSON(STORE_KEYS.categories, null),
      loadJSON(STORE_KEYS.goals, []),     loadJSON(STORE_KEYS.tasks, []),
      loadJSON(STORE_KEYS.roadmaps, []),
    ]);
    setProfile({ ...DEFAULT_PROFILE, ...(r[0] || {}) });
    setTasks(Array.isArray(r[3]) ? r[3] : []);
    // …plus categories, goals, roadmaps…
    setHydrated(true);
  })();
}, []);                        // ← empty deps: once per page load, never again

Five reads in parallel. That empty [] at the end is small and important: this never runs a second time, so the app can't notice changes made elsewhere.

5
PersistloadJSON — text back into objectslib/storage.js:68
export async function loadJSON(key, fallback) {
  try {
    const raw = await store.get(key);          // localStorage.getItem
    if (raw == null) return fallback;
    return JSON.parse(raw);
  } catch { return fallback; }              // ← swallows every error
}

And store was chosen once when the file first loaded, by feature detection: Claude storage if present, else localStorage, else memory (storage.js:37).

6
Persisthydrated flips — and the autosaves arm themselvesApp.jsx:128-132 · lib/storage.js:86
useAutoSave(STORE_KEYS.profile, profile, hydrated, report);
useAutoSave(STORE_KEYS.tasks,   tasks,   hydrated, report);   // ×5 total

// inside useAutoSave:
if (!hydrated) return;   // don't save the empty [] over real data

This guard is the whole reason hydrated exists. Without it, the empty arrays from step 2 would be written to disk before your data ever loaded.

Trap

Steps 5 and 6 don't quite hold hands. loadJSON returns the fallback on any failure, and step 4 calls setHydrated(true) unconditionally — it never checks whether the reads succeeded. So a failed load looks exactly like an empty account, the autosaves arm, and 350ms later real data is overwritten with [].

On localStorage this is rare. Over a network — dropped wifi, expired token, server restarting — it is routine. Fix this before the first deploy: make loadJSON report failure, and only set hydrated when all five reads actually came back.

Pattern Props down, callbacks up Views receive data and a function to call. They never reach for state that isn't theirs.
Pattern Copy, never mutate concat and map build new arrays. React re-renders on identity change, not content change.
Pattern One mutation, one function Four helpers cover every change a task can undergo. That's four API calls, mapped one to one.
Pattern Nothing is ever deleted deletedAt plus an alive() filter. The data stays; the screen looks away.

Three areas never appeared in these traces because they skip the pattern: RoadmapView, CategoryModal and SettingsView are handed setRoadmaps, setCategories and setProfile directly (App.jsx:340, 344, 352) — the raw state setters.
